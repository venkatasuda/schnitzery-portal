# Saved inventory count sessions

Implemented locally on 2026-10-24. Page: `/inventory/counts`, linked from Inventory Overview and the Stock worksheet. No production migration or deployment has been performed.

## Workflow

1. A manager starts or resumes the branch's single open draft. The database snapshots active catalogue identities, units, targets, Berlin count date and existing published-count evidence. Existing stock quantities are not copied into new draft quantities.
2. Enter quantities and **Save progress**. Blank means unknown; explicit zero is valid. Refreshing or using another device reloads the saved values. Unsaved edits remain only in the current browser page.
3. Save all lines, review the quantities, check the review confirmation and choose **Complete and publish**. Completion is atomic: all quantities are published together through the existing stock-event history triggers, or none are.
4. A completed session is read-only. Cancelling a draft preserves its saved snapshot and events without publishing it. The most recent 20 sessions are listed; older sessions remain directly addressable by `?session=<uuid>`.

This is a manager-reviewed completion, not an independent second-person approval workflow.

## Integrity and permissions

- Server actions recheck authentication, active account status, manager role and selected branch. The database independently checks the actor and branch access. An old page cannot silently save against a newly selected branch.
- Sessions, lines and events have RLS. Authenticated callers have SELECT only; staff cannot read them. Mutations go through an invoker RPC wrapping a checked definer function in the non-exposed private schema. No service key is used.
- A per-branch transaction lock protects start/resume and edits. Revision checks reject stale saves. Repeating a completed publish request returns its existing completion without duplicating counts.
- Completion locks the count/catalogue tables and checks the full published-count fingerprint and catalogue snapshot. Competing quick counts, edited published counts, archived products, added products, unit/name/target changes require cancelling and restarting the draft. Matching timestamps cannot hide a competing insertion.
- Every successful start/save/complete/cancel appends an immutable-to-clients event with actor, revision, timestamp and saved line changes. Normal table DELETE/UPDATE is unavailable to clients; a database administrator remains privileged.
- Count sessions retain their original count date when resumed later. Review that date before publishing; they do not silently become today's inventory.
