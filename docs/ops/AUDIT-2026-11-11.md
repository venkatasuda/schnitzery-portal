# Codebase audit — 11 Nov 2026

Scope: static read of `src/` (345 TS/TSX files, 88 pages), `src/app/globals.css` (1,249 lines), `supabase/migrations` (51), `supabase/schema`. Nothing was run in a browser for this audit, and RLS policies were not re-read one by one (see 4.1).

Stack: Next.js 16.4 (App Router, server actions, webpack), React 19, Supabase (Postgres + RLS + `private` SECURITY DEFINER functions), plain CSS with tokens in `globals.css`, Capacitor Android shell, Vercel.

## Verdict

| Area | State | Biggest gap |
|---|---|---|
| Data safety, tenancy | Strong | Labour rules are advisory, not checked at publish |
| Roster concurrency | Strong | None blocking |
| Design system | Half-migrated | Two generations of UI live side by side (tokens vs 425 inline styles) |
| Navigation | Weak | Two back-link patterns, ~25 sub-pages with none |
| Desktop layout | Weak on roster | Seven full-width day cards stacked on a 1,900 px screen |
| Realtime | Absent | No subscriptions anywhere in `src/` |

Three things in the brief already exist and should not be rebuilt: draft vs published roster (`roster_drafts` + `publish_roster`), optimistic-concurrency on roster save, and the rule-based scheduler with swap list and drag and drop.

### 1.3 Back navigation

> Correction (same day, while fixing): managers already had a parent link in the header (`ManagementLocation`, "Section / Hub"). The gap was real only for the employee app and for a few routes missing from the nav map. Fix shipped: header link reads "← Hub", `/prep`, `/shift`, `/day-close` added to the map, bottom-of-page back links removed, and `EmployeeBack` added for the employee app. No per-page `BackLink` was needed.

Two patterns exist and disagree:

- `.ui-back-link` (`globals.css:651`): centred text at the **bottom** of the page. 11 uses. Two of them are not back links at all but forward links styled with the class (`my-day/page.tsx:63`, `73`).
- `.inventory-back` (`globals.css:225`): top-left, 44 px target. 5 uses.

Sub-pages with no way back to their parent except the browser button or the main nav: `attendance/corrections`, `branches/[id]`, `staff/[id]`, `checklist/templates`, `checklist-status`, `schedule/compare`, `sales/imports`, `settings/integrations`, `inventory/connections`, `prep/plan`, `shift/delivery`, `roster`, `day-close`, `geofence`, `kiosks`, `incidents`, `notes`, `noshow`, `simulator`, `summary`, `timesheet`, `waste-branches`, `leave-calendar`, `directory`, `audit`. (Found by search for any back/parent link in the route folder; a few may be reachable from a hub tab, so confirm each when fixing.)

Fix: one component, always top-left, always a real link to the parent route (not `router.back()`, which leaves the app when the page was opened from a notification):

```tsx
// src/components/ui.tsx
export function BackLink({ href, children }: { href: string; children: ReactNode }) {
  return <Link href={href} className="back-link"><Icon e="←" size={16} /> {children}</Link>;
}
// PageHeader gains: back?: { href: string; label: ReactNode } and renders <BackLink> above the title.
```

Parent map lives in one object (`/roster → /schedule-hub`, `/staff/[id] → /staff`, `/prep/plan → /inventory` or `/shift` by role, …) so breadcrumbs can be derived from it later.

### 1.4 Employee: My Day → Availability

`AvailabilityForm.tsx`, `globals.css:1160-1166`.

- Unselected chips are `color: var(--text-muted)` on a transparent background with a 1 px border; selected is solid gold. Off and "not yet answered" look identical. Contrast of the muted text was not measured here; `scripts/checks/action-contrast.cjs` only covers the action colour.

## 2. Concurrency, tenancy, performance

### 2.1 Write contention

| Write | Protection | Verdict |
|---|---|---|
| Roster draft save (`schedule.ts:180-190`) | Compare-and-swap: update only where `roster_data` equals what the client loaded; insert races hit the unique key (23505) | Correct. A `version int` column would be cheaper than comparing the whole JSON, but this is not a bug |
| Publish (`20261111120000_roster_publish.sql:51-56`) | Advisory lock, `FOR UPDATE` on draft and live row, refuses if live ≠ draft base (40001) | Correct |
| Day close, cover decisions, inventory operations | Atomic `private` functions with locks and idempotency keys | Correct |
| Staff profile edit (`people.ts:132`) | None. `update(...).eq("id", staffId)` | Last write wins, but only for the fields sent. Two managers editing the same person's same field: the second silently wins |
| Shift times, staffing targets, staff tier (`shift-times.ts:55`, `staffing.ts:27`, `staff-tier.ts:22`) | Upserts, no version | Same: last write wins. Low traffic settings |

Fix for profile edits (the only one worth doing): send the `updated_at` the form loaded and add `.eq("updated_at", loadedAt)`; zero rows back means "changed by someone else, reload". I did not find an `updated_at` column on `users` in `production-schema.sql`; if it is missing, add it with a trigger in the same migration.

### 2.2 Query patterns

| Where | Problem |
|---|---|
| `leave.ts:89-92` | One `insert` per shift, awaited in a loop. Use one multi-row insert with `ignoreDuplicates` |
| `leave.ts:102-109` | For every shift × every teammate: `await notify` then `await push`, sequential. Ten teammates and three shifts is 60 round trips inside one server action. Collect the pairs, then `Promise.all` in one batch or one RPC |
| `my-branches.ts:21-27` | Per branch: `getOpsDashboard` (several queries) plus two counts. Fine at 3 branches, linear beyond; an owner with 15 branches fires roughly 100 queries per load. Needs one aggregate RPC when branch count grows |
| `live-attendance.ts:196` | One RPC per pending month (already marked in code) |
| `schedule.ts:202-207` | Publish re-reads the roster and pushes per person. Acceptable; the fan-out is `Promise.all` |

No Employees → Shifts → Availability nesting problem exists: the roster is one JSON row per branch-week, and the editor loads staff, availability and roster in three flat queries.

### 2.3 Frontend state

`roster/page.tsx` is one 437-line component with ~25 `useState` and no `useMemo` / `memo`. Every `setDragFrom` (drag start, drag end) re-renders all seven days and recomputes hours. With today's sizes (about 50 entries) this is not perceptible; it will be once the 7-column grid shows everything at once and cross-day drag is added. Extract `<RosterDay>` wrapped in `memo`, pass stable callbacks, and move the hours summary behind `useMemo([roster, staff])`. Only one file in `src/` uses `useTransition`; none use `useOptimistic`.

## 3. Blueprints

### 3.1 Draft / published

Already built: `roster_drafts` (with `base_data`), `weekly_roster.published_at/published_by`, `publish_roster`, status pill, Save draft / Publish / Discard. History is untouched because published rows keep living in `weekly_roster`. Nothing to add.

### 3.2 Optimistic UI

Roster edits are already local and instant; only Save and Publish talk to the server. Where a blueprint helps is single-tap actions that currently wait for the server (approve leave, mark notification read, claim cover):

```tsx
const [items, apply] = useOptimistic(serverItems, (cur, a: { id: string; patch: Partial<Item> }) =>
  cur.map((x) => (x.id === a.id ? { ...x, ...a.patch } : x)));
const [, start] = useTransition();
function approve(id: string) {
  start(async () => {
    apply({ id, patch: { status: "approved" } });        // paints immediately
    const r = await decideLeave(id, "approved");          // existing server action
    if (!r.ok) toast(r.error);                            // optimistic state drops on its own when the transition ends
    else await reload();
  });
}
```

### 3.3 Realtime

Use Supabase Realtime (already in the stack through `@supabase/supabase-js`); no new server needed. Signal only, then refetch through the existing loader so RLS and validation stay in one place:

```tsx
// src/lib/useBranchChanges.ts
export function useBranchChanges(table: "roster_drafts" | "weekly_roster" | "attendance_logs", branchId: string, onChange: () => void) {
  useEffect(() => {
    const ch = supabase.channel(`${table}:${branchId}`)
      .on("postgres_changes", { event: "*", schema: "public", table, filter: `branch_id=eq.${branchId}` }, onChange)
      .subscribe();
    return () => { void supabase.removeChannel(ch); };
  }, [table, branchId, onChange]);
}
```

In the roster editor: on a change by someone else, show "Changed by another manager — reload" when the local copy is dirty, reload silently when it is clean. Needs one migration (`alter publication supabase_realtime add table …`); I have not checked whether that publication is configured in production. Realistic latency is a few hundred ms, not a guaranteed 200.

## 4. Security and labour rules

### 4.1 Tenant isolation

What I verified in code:

- RLS is enabled on every table defined in the schema and migrations, and an event trigger (`rls_auto_enable`) turns it on for new ones.
- Server actions take the branch from the session (`getMe`), not from the client. Where a branch id is accepted (`ops-dashboard.ts:63-68`), it is checked by reading `branches` through RLS first.
- The four service-role routes (`create-staff`, `reset-staff-password`, `set-staff-active`, `unlock-login`) verify the caller, then branch and rank through `lib/auth/rank.ts` before using the admin client.
- Service-role use in `lib/queries` is limited to notifications, two atomic RPCs and branch names (`transfer.ts:30`, which deliberately lists all active branch names to any caller of that function; confirm that is intended).

What I did not do in this pass: re-read each of the ~90 tables' policies. The existing `scripts/checks/security-hardening.cjs` and `multi-branch-access.cjs` cover the main paths.

### 4.2 Labour rules

| Rule | Where it is applied | Enforced? |
|---|---|---|
| 11 h rest (§ 5 ArbZG) | `roster/smart.ts`, `roster/draft.ts` (automation), `roster/cover-check.ts` (cover approval warning), `queries/compliance.ts:98` (after the fact) | No. A manager can add a shift by hand and publish it |
| Minijob monthly cap | `pay/legal.ts` (`minijobCapOn`), scheduler, swap list, payroll pre-check | No, same gap |
| Contract weekly hours | Scheduler, swap list, hours panel | No |
| Rest across the week boundary | `smart.ts` does not look at the previous Sunday | Gap |

`saveRoster` (`schedule.ts:166-176`) validates shape, staff and branch only; `publish_roster` checks staleness only. The roster editor shows one warning, "not available" (`roster/page.tsx:376`).

Fix: one pure function `checkRoster(roster, staff, shiftTimes, prevSunday, monthToDate)` returning violations per entry, reusing `cover-check.ts` and `legal.ts`. Call it in the editor (badges on rows) and in `publishRoster` before the RPC. Rest violations block publish; Minijob and contract overruns need an explicit "publish anyway" with a reason written to `audit_logs`. Blocking everything outright would stop a manager covering a sick call, which is a business decision for you.
